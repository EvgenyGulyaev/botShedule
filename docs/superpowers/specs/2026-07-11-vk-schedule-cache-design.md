# Кэш VK-пользователей и расписаний

## Цель

Сократить повторные запросы к VK API и TGPI на слабом сервере, сохранив ограниченное потребление памяти и текущее пользовательское поведение.

## VK-кэш

`vk.Bot` хранит кэш имён по числовому VK user ID. Запись содержит имя и время последней проверки.

- TTL: один час.
- Максимальный размер: 1000 записей.
- Повторный запрос в пределах TTL не вызывает `UsersGet`.
- Первый запрос после TTL синхронно обновляет имя.
- При ошибке обновления возвращается старое имя, а следующая попытка откладывается на час.
- Если старого имени нет, возвращается текущая пустая строка, а следующий запрос снова пытается получить данные.

Один mutex защищает map и остаётся захваченным во время запроса VK. Это намеренно ограничивает параллельные обращения к API и предотвращает stampede. Для текущей нагрузки слабого сервера простота и ограничение конкуренции важнее параллельной загрузки разных пользователей.

## Кэш расписаний

Существующий `tgpi.Client` хранит расписания по ключу `{TypeEl, ID}`. Запись содержит `[]Schedule` и время последней проверки.

- TTL: пять минут.
- Максимальный размер: 1000 записей.
- Повторный запрос одного элемента в пределах TTL не выполняет HTTP-запрос.
- Первый запрос после TTL синхронно обновляет расписание.
- При ошибке HTTP, статусе вне 2xx или ошибке парсинга возвращается старое расписание, а следующая попытка откладывается на пять минут.
- Если старого расписания нет, возвращается текущий пустой результат, а следующий запрос снова пытается загрузить данные.

Один mutex сериализует обновления расписаний и предотвращает несколько одновременных запросов к TGPI.

## Ограничение памяти

Каждый кэш ограничен 1000 записями. Перед добавлением новой записи при достижении лимита выполняется линейный поиск самой старой записи, после чего она удаляется. Этот O(n) проход происходит только при заполненном кэше; отдельная LRU-структура и фоновая очистка не нужны.

Обновление существующего ключа не вызывает вытеснение. Пустой успешный результат кэшируется так же, как непустой.

## Структура кода

- `iternal/adapters/vk/bot.go`: состояние VK-кэша и его инициализация.
- `iternal/adapters/vk/user.go`: cache lookup, загрузка имени и вытеснение старой записи.
- `iternal/usecase/tgpi/groups.go`: дополнительные поля общего `Client` для schedule cache.
- `iternal/usecase/tgpi/schedule.go`: cache lookup, HTTP-загрузка расписания и вытеснение.

Новый общий generic cache не создаётся: два значения и способы загрузки различаются, а небольшое локальное дублирование проще отдельной абстракции.

## Ошибки и совместимость

Публичные сигнатуры `getUserName(int) string` и `GetSchedule(*El) []Schedule` сохраняются. Формат сообщений, часовой кэш справочника и 15-секундные HTTP timeout не меняются.

Schedule loader начинает проверять HTTP status до парсинга. Парсер должен возвращать ошибку вместо среза строки с panic при неожиданной странице, чтобы не заменять рабочий кэш повреждённым результатом.

## Проверка

Для обоих кэшей тестируются:

- cache hit в пределах TTL;
- обновление после TTL;
- один upstream-запрос при конкурентных обращениях;
- stale fallback и подавление повторных запросов во время ошибки;
- вытеснение самой старой записи при лимите;
- кэширование успешного пустого результата.

Дополнительно выполняются полный `go test`, race detector, `go vet` и сборка `cmd/bot`.

## Вне объёма

- Фоновые обновления и очистка.
- Распределённый кэш.
- Новые зависимости.
- Изменение TTL через конфигурацию.
- Кэш Telegram-пользователей.
