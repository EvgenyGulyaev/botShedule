# Оптимизация оставшихся горячих путей

## Цель

Дополнительно снизить CPU, выделения памяти, логирование и число краткоживущих горутин на слабом сервере без новых зависимостей и без изменения ответов бота.

## Согласованный объём

Реализуются четыре ранее предложенных изменения:

1. Отключение debug-режима Telegram API и удаления лога каждого входящего сообщения.
2. Снижение таймаута запросов к TGPI с 1000 до 15 секунд.
3. Предвычисление строки для регистронезависимого поиска при часовой загрузке справочника.
4. Синхронная постановка пользовательского события в NATS без отдельной горутины на каждое сообщение.

VK-кэш, кэш расписаний, удаление `cmd/scrapper` и несвязанный рефакторинг остаются вне объёма.

## Telegram logging

`tgbotapi.BotAPI.Debug` остаётся со стандартным значением `false`. Лог входящего имени пользователя и текста удаляется. Ошибки запуска и отправки сообщений продолжают логироваться.

Это сокращает форматирование строк и запись логов в основном цикле, а также исключает сохранение пользовательских сообщений в техническом логе.

## HTTP timeout

Оба существующих клиента TGPI используют `15 * time.Second` вместо `1000 * time.Second`. Новая настройка и отдельный слой конфигурации не вводятся: значение одинаково для справочника и расписания.

Истечение таймаута сохраняет существующее внешнее поведение: методы возвращают пустой результат либо ранее кэшированный справочник.

## Предвычисленный поиск

`El` получает приватное поле `searchName`. Оно заполняется через `strings.ToLower` один раз во время декодирования часового справочника для групп, аудиторий и преподавателей.

`filterGroups` приводит к нижнему регистру только пользовательскую маску и сравнивает её с `searchName`. Для элементов, созданных вручную внутри пакета без декодирования, сохраняется fallback к `strings.ToLower(el.Name)`.

Цена — одна дополнительная нормализованная строка на элемент справочника в течение часа. Это заменяет примерно тысячу строковых выделений на каждый поиск одним набором строк при обновлении кэша.

## NATS publish

В Telegram- и VK-обработчиках `user.Publish()` вызывается напрямую вместо `go user.Publish()`. Сам `nats.Conn.Publish` ставит сообщение во внутренний буфер соединения; дополнительная прикладная горутина не нужна.

Порядок действий сохраняется: пользовательское событие публикуется до проверки блокировки и формирования ответа.

## Проверка

- Тест декодирования подтверждает заполнение `searchName` для всех типов элементов.
- Существующие тесты подтверждают регистронезависимый поиск и порядок результатов.
- Benchmark использует подготовленные элементы и сравнивается с текущей базой: около `114 KB/op` и `1011 allocs/op`.
- Полный набор проверяется через `go test`, race detector и `go vet`.
- Diff отдельно проверяется на отсутствие VK-кэша, кэша расписаний и новых зависимостей.

## Критерии готовности

- Telegram debug и лог текста входящего сообщения отключены.
- Оба TGPI-клиента освобождают зависший запрос не позднее 15 секунд.
- Поиск по подготовленному справочнику не нормализует каждое имя заново.
- Обработчики не создают горутину для каждого NATS publish.
- Пользовательские ответы, часовой TTL и stale fallback не меняются.
- Все тесты, race detector и `go vet` проходят.
