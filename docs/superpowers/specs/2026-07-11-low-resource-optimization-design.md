# Оптимизация бота для слабого сервера

## Цель

Снизить процессорную и сетевую нагрузку при обработке сообщений без изменения пользовательского поведения бота. Справочник групп, преподавателей и аудиторий может быть устаревшим не более чем на один час.

## Текущее состояние

Каждое сообщение, не являющееся командой, вызывает `GetGroups`. Метод заново загружает с `edu.tgpi.ru` полный справочник и затем фильтрует его. Фильтрация создаёт горутину для каждого элемента, но защищает проверку и добавление результата общим mutex, поэтому работа фактически сериализована с дополнительными затратами. Команда также вычисляется дважды в `GetAnswer`.

Проект проходит `go test ./...`, `go test -race ./...` и `go vet ./...`, но собственных тестов пока нет.

## Решение

### Часовой кэш справочника

Существующий `tgpi.Client` будет хранить:

- последний успешно загруженный полный список `[]El`;
- время успешной загрузки;
- mutex для защиты кэша и предотвращения одновременных обновлений.

`GetGroups` сначала получает полный справочник через внутренний метод кэша, а затем фильтрует его по запросу пользователя. Пока кэш моложе одного часа, сетевой запрос не выполняется.

Обновление выполняется синхронно первой горутиной, обнаружившей истёкший кэш. Остальные запросы ждут тот же mutex вместо запуска параллельных HTTP-запросов. Фоновый worker, таймер и новая зависимость не нужны.

Если обновление завершилось ошибкой, клиент возвращает последний успешно загруженный справочник, даже если он старше часа. Неуспешный или некорректный ответ не заменяет рабочий кэш. Если успешных данных ещё не было, сохраняется текущее поведение: пользователь получает пустой результат.

Ответы расписания не кэшируются: они меняются чаще, а справочник является главным повторяющимся запросом.

### Последовательная фильтрация

`filterGroups` станет обычным циклом:

1. Поисковая строка один раз приводится к нижнему регистру.
2. Элементы проверяются последовательно через `strings.Contains`.
3. Совпадения добавляются в результирующий slice в исходном порядке.

Это удаляет горутину на каждый элемент, semaphore, `WaitGroup` и mutex. Для коротких строковых проверок на слабом сервере такой путь требует меньше CPU и памяти и даёт детерминированный порядок результатов.

### Удаление повторной работы

`HandlerMessage.GetAnswer` вызовет `HandlerCommand` один раз и переиспользует результат.

## Ошибки и HTTP

Внутренний метод загрузки должен отличать успешный пустой ответ от ошибки. Кэш обновляется только после успешного HTTP-ответа и успешного декодирования JSON. Тело ответа всегда закрывается.

Публичное поведение `GetGroups(string) []El` сохраняется, чтобы не расширять изменение на обработчики и адаптеры.

## Проверка

В пакет `tgpi` добавляются небольшие тесты без сторонних библиотек:

- фильтрация без горутин сохраняет порядок и выполняет регистронезависимый поиск;
- два запроса в пределах часа вызывают тестовый HTTP-сервер один раз;
- истёкший кэш обновляется;
- одновременные обращения приводят к одному обновлению;
- ошибка обновления оставляет доступными старые данные.

Также добавляется benchmark фильтрации, чтобы сравнить стоимость до и после изменения. Итоговая проверка:

```sh
go test ./...
go test -race ./...
go vet ./...
go test -bench=. -benchmem ./iternal/usecase/tgpi
```

## Критерии готовности

- Не более одного запроса справочника в час в рамках одного процесса при успешном ответе upstream.
- Нет горутины на каждый элемент справочника.
- Порядок результатов стабилен и совпадает с порядком upstream.
- При временной ошибке upstream ранее загруженный справочник продолжает работать.
- Пользовательские ответы и публичные сигнатуры не меняются.
- Все тесты, race detector и `go vet` проходят.

## Вне объёма

- Кэширование расписаний.
- Постоянное хранение кэша на диске или в базе данных.
- Распределённый кэш для нескольких экземпляров бота.
- Фоновое обновление и конфигурируемый TTL.
- Обновление зависимостей и несвязанный рефакторинг.
